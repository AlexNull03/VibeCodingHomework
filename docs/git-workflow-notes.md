# Git 版本管理实验记录

在 VS Code 的源代码管理面板中完成一次完整的分支—暂存—提交—切换—合并流程。

## 实验步骤

| 步骤 | 操作 | VS Code 入口 | 对应 Git 命令 |
| --- | --- | --- | --- |
| 1 | 从 `main` 创建并切换到功能分支 | 状态栏左下角分支名 → 创建新分支 | `git switch -c feature/git-version-mgmt-demo` |
| 2 | 新增本文件，改动出现在"更改"列表 | 源代码管理侧栏（Ctrl+Shift+G） | `git status` |
| 3 | 暂存单个文件 | 文件右侧 `+` | `git add docs/git-workflow-notes.md` |
| 4 | 填写提交信息并提交 | 提交框，`Ctrl+Enter` | `git commit -m "..."` |
| 5 | 切回主干，确认主干看不到本分支改动 | 状态栏分支名 → `main` | `git switch main` |
| 6 | 把功能分支合并回主干 | 源代码管理 → 图表 → 分支 → 合并 | `git merge feature/git-version-mgmt-demo` |
| 7 | 查看提交图，确认分支拓扑 | 源代码管理 → 图表 | `git log --graph --oneline` |

## 观察到的现象

1. 分支创建后，状态栏分支名立即由 `main` 变为 `feature/git-version-mgmt-demo`，工作区文件内容不变，说明此刻两个分支指向同一个提交。
2. 新建的文件在"更改"区标记为 `U`（未跟踪），暂存后变为 `M`/已暂存并从"更改"移入"暂存的更改"，这一步决定了哪些内容进入下一次提交。
3. 切回 `main` 后该文件从工作区消失——分支隔离的直接体现；合并回来之后它重新出现。
4. 图表视图按提交时间画出分支线，可以直观看到功能分支的提交是在哪一步并入主干的，比命令行 `git log` 更容易核对。

## 结论

日常改动先开分支、小步提交，主干始终保持可用；合并前用图表视图核对提交范围。相比直接在 `main` 上提交，分支方式在改错时只需丢弃分支，不会污染主干历史。
